## ۲. اصول طراحی کامپوننت‌های با قابلیت استفاده مجدد و سفارشی‌سازی (Reusability & Customizability)

تمامی کامپوننت‌ها باید از الگوی **Compound Components** و **Slot-Based APIs** پیروی کنند:

### ۲.۱. قوانین طراحی در Jetpack Compose (Android)
1. **جداسازی کامل وضعیت (State Hoisting):**
   - هیچ کامپوننت UI نباید مستقیماً به `ViewModel` یا وابستگی خارجی وصل شود.
   - فرمول استاندارد: `MyComponent(state: MyUiState, onAction: (MyUiAction) -> Unit, modifier: Modifier = Modifier, ...)`
2. **پشتیبانی از Slot API:**
   - کامپوننت‌ها نباید محتوای داخلی را هاردکد کنند. برای بخش‌های فرعی (Icon, Leading, Trailing, Actions, Content) باید پارامترهای `@Composable (() -> Unit)?` در نظر گرفته شود.
3. **انعطاف‌پذیری استایل (Theming & Styling):**
   - هیچ رنگ (Color) یا اندازه قلم هاردکد شده مجاز نیست؛ الزام استفاده از `MaterialTheme.colorScheme` و `MaterialTheme.typography`.
   - کامپوننت باید به صورت پیش‌فرض زیباترین حالت را داشته باشد، اما اجازه تغییر رنگ، شکل (Shape) و فاصله (Padding) را از طریق `Modifier` یا `Colors / Style Object` به مصرف‌کننده بدهد.

### ۲.۲. قوانین طراحی در React / TypeScript (Web)
1. **طراحی اتمیک و ترکیب‌پذیر (Compound Components):**
   - برای کامپوننت‌های پیچیده مثل کارت یا دیالوگ: `Card`, `Card.Header`, `Card.Body`, `Card.Footer`.
2. **قرارداد Props صریح و نوع‌گذاری‌شده:**
   - پرهیز از `any`؛ استفاده از Generic types و `React.ComponentPropsWithRef`.
   - پشتیبانی از تم‌های تیره و روشن از طریق متغیرهای CSS و توکن‌های طراحی یکپارچه.

## ۳. استاندارد شکستن صفحات (Screen Decomposition Standard)

برای جلوگیری از ایجاد فایل‌های بزرگ و غیرقابل نگهداری (مانند تجربیات قبلی فایل‌های بالای ۱۰۰۰ خط):

1. **قانون سقف ۳۰۰ خط:** هیچ فایل صفحه (Screen/Page) نباید از ۳۰۰ خط فراتر برود.
2. **تفکیک لایه‌ای هر صفحه به حداقل ۴ زیرکامپوننت مستقل:**
   - `HeaderSection`: نوار عنوان، دکمه‌های اقدام سریع و ناوبری.
   - `MetricsSummarySection`: کارت‌های خلاصه آماری و مانده‌ها.
   - `MainContentSection`: فهرست داده‌ها با مدیریت حالت‌های Empty/Loading/Error.
   - `ActionBottomBar / Sheet`: اکشن‌های ورودی، کیبورد یا دکمه‌های شناور.
3. **جداسازی Stateful از Stateless:**
   - صفحه اصلی (`*Screen.kt` یا `*Page.tsx`) مسئول جمع‌آوری State و رویدادهاست.
   - زیرکامپوننت‌ها کامپوننت‌های خالص (Pure / Presentational) هستند که تست و رندر مجدد آن‌ها فوق‌العاده سریع و بهینه است.

## ۴. استراتژی جامع پیش‌نمایش (Preview Architecture)

هیچ کامپوننت یا صفحه‌ای بدون پیش‌نمایش تصویری قابل ادغام نیست:

### ۴.۱. الزامات پیش‌نمایش در اندروید (Jetpack Compose Previews)
هر کامپوننت باید حداقل شامل پیش‌نمایش‌های زیر باشد:
1. **Light Mode Preview** (در ابعاد استاندارد تلفن همراه).
2. **Dark Mode Preview** (برای اعتبارسنجی کنتراست رنگ‌های گرم/تیره).
3. **Dynamic Color Preview** (تست هماهنگی با تم پالت Material You اندروید ۱۲+).
4. **حالت‌های چندگانه محتوا:**
   - حالت بارگذاری (Loading / Shimmer Skeleton).
   - حالت داده پر (Full Content با متن‌های طولانی فارسی).
   - حالت خالی (Empty State با دکمه اقدام).
   - حالت خطا (Error State).
5. **اعتبارسنجی RTL:** تمام Previewها باید چینش راست‌به‌چپ متون فارسی و آیکون‌های جهت‌دار را نمایش دهند.

### ۴.۲. الزامات پیش‌نمایش در وب (Web Preview Gallery)
- تمام کامپوننت‌های اشتراکی در مسیر `web/src/preview/PreviewGallery.tsx` با کنترل‌های تعاملی (Knobs) برای تغییر وضعیت‌ها، زبان و تم ثبت می‌شوند.

## ۵. پروتکل بازبینی همکار ارشد (Senior Peer Code Review Protocol)

پیش از تأیید هر کد، دو مهندس ارشد (نویسنده + بازبین Skeptic) باید چک‌لیست زیر را امضا کنند:

```markdown
### چک‌لیست بازبینی کد (Senior Rubric Check):
1. [ ] صحت منطق (Correctness): آیا بدون نیاز به اینترنت و در شرایط آفلاین رفتار پایداری دارد؟
2. [ ] مرزهای تمیز و ماژولار بودن: آیا کامپوننت‌ها به اندازه کافی شکسته شده‌اند (کمتر از ۳۰۰ خط)؟
3. [ ] قابلیت استفاده مجدد (Reusability): آیا props هاردکد نشده و برای شرایط مختلف قابل کاستوم است؟
4. [ ] انطباق با RTL و بومی‌سازی: آیا در زبان فارسی متون، فونت‌ها و آیکون‌ها بدون باگ نمایش داده می‌شوند؟
5. [ ] مدیریت خطاهای مرزی: مقادیر صفر، اعداد بسیار بزرگ ریالی/تومانی و رشته‌های نامعتبر هندل شده‌اند؟
6. [ ] پیش‌نمایش (@Preview): آیا کامپوننت در حالت‌های روشن، تاریک و داده‌های مختلف دارای Preview است؟
7. [ ] کیفیت‌گیت بیلد: آیا دستور `./scripts/verify-all.sh` بدون هیچ‌گونه هشدار یا خطایی سبز است؟
```
